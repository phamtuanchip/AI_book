Phần II — Prompting & công cụ AI hỗ trợ lập trình

Chương 7: Prompting cho code

Chương này áp khung 4 thành phần (Chương 5) và các kỹ thuật nâng cao (Chương 6) vào 5 tình huống lập trình phổ biến nhất: sinh code mới, giải thích code, refactor, sinh test, và debug. Mỗi tình huống có một "công thức" prompt riêng vì tiêu chí thành công khác nhau.

Sinh code mới

Rủi ro lớn nhất khi sinh code mới là mô hình đoán bừa các ràng buộc bạn không nói ra — phiên bản ngôn ngữ, thư viện được phép dùng, convention của team. Prompt tốt phải chặn trước các điểm mơ hồ đó:

Vai trò: Bạn là backend engineer dùng Go.
Bối cảnh: Service xử lý order trong hệ thống microservice, dùng
PostgreSQL qua sqlx, không dùng ORM.
Yêu cầu: Viết hàm CreateOrder(ctx, input) nhận input đã validate, insert
vào bảng orders, trả về order kèm ID vừa tạo. Xử lý lỗi trùng khoá
(duplicate key) trả về error riêng biệt.
Định dạng: Chỉ code Go, không giải thích dài dòng, comment ngắn ở chỗ
logic không hiển nhiên.

Giải thích code

Khi nhờ AI giải thích code lạ (thường gặp khi vào codebase mới — sẽ nói kỹ hơn ở Chương 9), hãy nói rõ mức độ giải thích bạn cần — tổng quan kiến trúc hay chi tiết từng dòng — nếu không sẽ nhận một đoạn diễn giải chung chung ít giá trị:

"Giải thích đoạn code sau ở 2 tầng:
1. Tổng quan: hàm này giải quyết vấn đề gì, được gọi từ đâu (dựa trên
   ngữ cảnh có thể suy luận được)?
2. Chi tiết: đi qua từng khối logic chính, giải thích TẠI SAO nó được
   viết như vậy (không chỉ mô tả nó làm gì).

{dán code}"

Refactor

Refactor là tình huống dễ "mất kiểm soát" nhất nếu không giới hạn phạm vi — mô hình có xu hướng viết lại nhiều hơn cần thiết. Luôn khoanh vùng rõ mục tiêu và những gì không được đổi:

"Refactor hàm sau để giảm độ phức tạp cyclomatic (đang lồng 4 tầng
if/else). Ràng buộc:
- Giữ nguyên signature của hàm (tên, tham số, kiểu trả về).
- Không đổi hành vi — liệt kê rõ nếu có thay đổi hành vi dù nhỏ.
- Ưu tiên early return thay vì lồng điều kiện.
- Không thêm dependency mới."
Luôn kèm test khi refactor bằng AI Nếu chưa có test cho đoạn code định refactor, hãy yêu cầu AI viết test cho hành vi hiện tại trước, chạy xanh, rồi mới refactor. Không có test, bạn không có cách nào xác nhận "không đổi hành vi" thực sự đúng.

Sinh test

Yêu cầu mặc định "viết test cho hàm này" thường chỉ ra test cho đường đi thuận (happy path). Prompt tốt phải chủ động liệt kê các nhóm case cần bao phủ:

"Viết unit test cho hàm {tên hàm} bằng {framework test}. Bao phủ đủ 4
nhóm case:
1. Happy path (input hợp lệ điển hình)
2. Input biên (rỗng, null/undefined, giá trị 0, giá trị âm nếu áp dụng)
3. Input không hợp lệ (sai kiểu, thiếu field bắt buộc)
4. Case gây lỗi/exception — assert đúng loại lỗi được throw

Mỗi test đặt tên mô tả rõ case đang kiểm tra."

Debug

Đây là nơi chain-of-thought (Chương 6) phát huy tác dụng rõ nhất — đừng chỉ dán lỗi và hỏi "sửa sao", hãy cung cấp đủ ngữ cảnh và yêu cầu mô hình suy luận có hệ thống thay vì đoán bừa:

"Tôi gặp lỗi sau khi chạy hàm {tên hàm}:

Lỗi: {message lỗi đầy đủ + stack trace}
Code liên quan: {dán code}
Đã thử: {những gì bạn đã kiểm tra/loại trừ, nếu có}

Trước khi đề xuất fix, hãy: (1) liệt kê tối đa 3 nguyên nhân khả dĩ dựa
trên message lỗi, (2) với mỗi nguyên nhân, chỉ ra dòng code liên quan,
(3) đề xuất cách kiểm tra nhanh nguyên nhân nào đúng trước khi sửa."
Vì sao nên khai báo "đã thử những gì" Không cung cấp thông tin này, mô hình dễ lặp lại chính hướng debug bạn đã loại trừ — vì nó không có cách nào biết bạn đã thử gì, dẫn tới vòng lặp hỏi-đáp lãng phí thời gian cả hai bên.

Prompting cho code legacy/thiếu tài liệu

Một tình huống không nằm gọn trong 5 nhóm trên nhưng rất phổ biến: codebase cũ, không có tài liệu, không có test, người viết ban đầu đã nghỉ việc. Cách tiếp cận khác với "giải thích code" thông thường vì mục tiêu không chỉ là hiểu, mà là hiểu đủ an toàn để thay đổi:

"Đây là module legacy không có tài liệu: {dán code}. Trước khi tôi thay
đổi bất cứ điều gì, hãy giúp tôi:
1. Liệt kê mọi nơi module này được gọi đến (dựa trên các dấu hiệu có thể
   suy luận từ code — tên hàm, import, comment cũ).
2. Chỉ ra các hành vi 'ẩn' cần cẩn thận (side effect, biến toàn cục bị
   thay đổi, thứ tự gọi hàm quan trọng).
3. Đề xuất bộ test tối thiểu để 'chụp lại' hành vi hiện tại trước khi
   tôi sửa bất cứ gì (characterization test)."

Kỹ thuật "characterization test" (viết test ghi lại hành vi hiện tại, kể cả khi không chắc hành vi đó có đúng theo ý định ban đầu hay không) là bước an toàn bắt buộc trước khi refactor code legacy — làm đúng thứ tự này giúp AI hỗ trợ hiệu quả hơn nhiều so với yêu cầu "sửa luôn" ngay từ đầu.

Chọn đúng ngữ cảnh khi thay đổi nhiều file

Nhắc lại "context rot" ở Chương 4: nhồi toàn bộ codebase vào một prompt không đảm bảo chất lượng tốt hơn — thường ngược lại. Khi một thay đổi chạm vào nhiều file, hãy chọn lọc theo mức độ liên quan thay vì đưa "tất cả cho chắc":

  • File cần sửa trực tiếp: luôn đưa vào đầy đủ.
  • File định nghĩa interface/type được dùng: đưa vào nếu thay đổi có khả năng ảnh hưởng đến hợp đồng (contract) giữa các module.
  • File chỉ tham khảo convention (ví dụ 1-2 file mẫu cùng pattern): đưa 1 ví dụ đại diện, không cần đưa toàn bộ các file tương tự.
  • Phần còn lại của codebase: để CLI agent (Chương 9) tự tìm kiếm khi cần (qua tool đọc file), thay vì nhồi sẵn vào context ngay từ đầu.
