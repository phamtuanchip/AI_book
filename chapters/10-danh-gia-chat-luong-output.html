Đây là chương quan trọng nhất Phần II, dù ngắn gọn nhất. Prompt giỏi đến đâu cũng vô nghĩa nếu bạn chấp nhận output mà không kiểm chứng — nhắc lại hallucination và automation bias ở Chương 4. Chương này biến điều đó thành thói quen review cụ thể.

"Vibe coding" là gì, và vì sao nguy hiểm

Vibe coding — thuật ngữ chỉ việc chấp nhận code do AI sinh ra chỉ vì nó "chạy được" hoặc "trông ổn", không đọc kỹ, không hiểu logic, không kiểm tra edge case. Với việc thử nghiệm cá nhân, prototype nhanh, đây có thể là cách làm hợp lý. Nhưng đưa vào code chạy sản phẩm thật, nó tích luỹ nợ kỹ thuật vô hình: bug tiềm ẩn không ai hiểu tại sao xảy ra, vì không ai — kể cả người "viết" ra nó — thực sự đọc và hiểu logic.

Ranh giới cần phân biệt rõ Dùng AI để tăng tốc viết code là tốt. Dùng AI để thay thế việc hiểu code là rủi ro. Bạn vẫn phải là người chịu trách nhiệm giải thích được code trong PR của mình khi bị hỏi — dù ai/cái gì đã viết ra nó.

Checklist review code do AI sinh ra

Coi code AI-generated như code của một thực tập sinh rất nhanh nhưng chưa có kinh nghiệm ngữ cảnh dự án — nhanh, siêng, nhưng cần review kỹ như bất kỳ PR nào khác, cộng thêm vài điểm đặc thù:

  • Đúng yêu cầu, không thừa: có làm đúng những gì được yêu cầu, không tự ý thêm tính năng/thay đổi ngoài phạm vi (mô hình có xu hướng "hào phóng" thêm code không ai nhờ)?
  • Ảo giác API: hàm/thư viện/tham số được dùng có thực sự tồn tại? Kiểm tra với tài liệu chính thức nếu không chắc, đặc biệt với thư viện ít phổ biến (nhắc lại Chương 4).
  • Edge case & xử lý lỗi: input rỗng, null, timeout, dữ liệu vượt giới hạn — có được xử lý hay bị bỏ qua?
  • Bảo mật: có lỗ hổng injection, có validate input từ người dùng không, có hardcode secret nào không (xem thêm Chương 23 cho hệ thống agentic)?
  • Nhất quán với codebase: có theo đúng convention, pattern, cấu trúc thư mục đã có, hay tạo ra một "đảo phong cách" riêng biệt?
  • Hiệu năng ở quy mô thực tế: code chạy đúng với dữ liệu mẫu nhỏ, nhưng có vấn đề N+1 query, vòng lặp lồng không cần thiết, hay load toàn bộ dữ liệu vào bộ nhớ không?

Ví dụ minh hoạ: áp checklist vào một đoạn code thật

// Code do AI sinh ra khi được yêu cầu: "viết hàm tìm user theo email"

async function findUserByEmail(email) {
  const query = `SELECT * FROM users WHERE email = '${email}'`;
  const result = await db.query(query);
  return result.rows[0];
}

Áp checklist Chương 10 vào đoạn code trên:

Mục checklistKết quả
Đúng yêu cầu, không thừaPASS — đúng chức năng được yêu cầu
Ảo giác APIPASS — db.query là API thật của dự án
Edge case & xử lý lỗiFAIL — không xử lý khi email là undefined, không xử lý khi không tìm thấy user (trả undefined im lặng)
Bảo mậtFAIL nghiêm trọng — nối chuỗi trực tiếp email vào câu SQL tạo lỗ hổng SQL injection kinh điển
Nhất quán conventionCần kiểm tra — dự án có đang dùng query builder/ORM ở nơi khác không, hay quen dùng raw SQL với parameter binding?
 
// Sau khi review theo checklist, yêu cầu AI sửa lại:

async function findUserByEmail(email) {
  if (!email) throw new Error("email là bắt buộc");
  const result = await db.query(
    "SELECT * FROM users WHERE email = $1",
    [email]                         // <- parameter binding, chặn SQL injection
  );
  return result.rows[0] ?? null;    // <- rõ ràng khi không tìm thấy
}
Vì sao ví dụ này quan trọng Code gốc "chạy được" và trông hoàn toàn bình thường với người đọc lướt — đây chính xác là kiểu lỗi mà "vibe coding" (đầu chương) bỏ lọt, và checklist có cấu trúc mới bắt được một cách hệ thống thay vì tình cờ.

Kiểm thử vẫn là tuyến phòng thủ quan trọng nhất

Test tự động (unit test, integration test) là cách khách quan nhất để xác nhận code — do AI hay con người viết — thực sự đúng, không phụ thuộc vào việc đọc code có "trông ổn" hay không. Ba nguyên tắc khi kết hợp AI với testing:

  1. Không để AI tự viết test rồi tự chấm nó "pass" mà không có ai review test đó có thực sự kiểm tra đúng hành vi mong muốn không — test viết sai vẫn "xanh" nhưng vô giá trị.
  2. Test hành vi hiện tại trước khi refactor bằng AI (đã nhắc ở Chương 7) — không có test nền, bạn không có cách nào biết "không đổi hành vi" có thực sự đúng.
  3. CI/pipeline vẫn phải là cửa chặn cuối cùng — không merge code (dù AI hay người viết) chỉ dựa trên việc nó "chạy được trên máy tôi".
